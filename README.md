# CRC32 Files Check

CRC32 files check monitors regular files in a directory for content changes. It records
their CRC32 checksums at startup, periodically checks for changes, and reports updates to
stdout and syslog.

CRC32 files check отслеживает изменения обычных файлов в заданном каталоге. При запуске
программа запоминает их CRC32, затем периодически проверяет содержимое и сообщает об
изменениях в stdout и syslog.

## Описание

Программа отслеживает набор файлов, обнаруженный при запуске. Каталог и интервал проверки
задаются аргументами командной строки или переменными окружения.

CRC32 используется здесь как быстрый способ обнаружения изменений, а не как криптографический механизм контроля целостности. Программа не обеспечивает аутентифицированную проверку и не предназначена для обнаружения всех изменений самого каталога, например появления новых файлов.

## Разработка и проверка изменений

**Опорные символы для изменения поведения:**

1. `CRC32` и `crc32_lib` - вычисление контрольной суммы и вспомогательная реализация; при
   изменении проверки файлов учитывайте ранее открытые дескрипторы.

**Основные точки изменения:**

- `src/CRC32_files_check.c` - основной цикл наблюдения, параметры запуска и сообщения об изменениях;
- `src/crc32.c` - вычисление CRC32;
- `test/test.sh` - сценарий проверки изменений файлов.

**Границы тестового сценария:** `test/test.sh` удаляет каталог `test` относительно текущего рабочего каталога и вызывает `pkill -f` по имени программы. Кроме того, `exec_path` в сценарии задан как `../build/CRC32-files-check`, а пресет `release` создаёт `build/release/CRC32-files-check`. До запуска изолируйте рабочий каталог и согласуйте путь к бинарнику; тестовый скрипт не следует запускать вслепую на рабочей машине. Отдельно проверьте изменение содержимого открытого файла, замену пути через `rename()` и появление нового файла: последние два события сейчас не подразумевают повторного открытия или сканирования.

**Файлы сборки:** `CMakeLists.txt` определяет цели и исходники утилиты, а `CMakePresets.json` - профили конфигурации. При изменении флагов компиляции проверяйте оба файла.

**Проверка изменений:** После изменения алгоритма контрольной суммы проверьте `test/test.sh`; после изменения наблюдения или вывода повторите сценарий запуска из раздела "Запуск". Сохраните одинаковую интерпретацию CRC32 при начальном сканировании и повторной проверке.

## Сборка

```sh
cmake --preset release
cmake --build --preset release
```

Исполняемый файл:

```text
build/release/CRC32-files-check
```

## Запуск

```text
Commands:
  Required parameters:
    -f  "/test/"  Directory to check
    -t  "60"      Check interval in seconds
```

Пример:

```sh
./build/release/CRC32-files-check -f /srv/data -t 60
```

Те же параметры можно задать через окружение:

```sh
CHECK_FOLDER=/srv/data CHECK_FOLDER_TIME=60 ./build/release/CRC32-files-check
```

Параметры командной строки переопределяют значения из окружения.

## Как работает

При старте программа проходит по обычным файлам в указанном каталоге и считает для них CRC32. Затем через заданный интервал контрольные суммы сравниваются со значениями **предыдущей проверки**: после каждого цикла код обновляет сохранённый CRC32 даже при `FAIL`. Если содержимое больше не меняется, следующий цикл выдаст `OK`, а не повторит предупреждение о первом изменении.

Проект предназначен прежде всего для простого мониторинга изменений файлов, когда важны минимальная зависимость от внешних библиотек и небольшой объём кода.

**Ограничения параметров:** при `-f` длина пути проверяется перед копированием
в буфер `PATH_MAX`, но `CHECK_FOLDER` копируется через `strcpy()` без
аналогичной проверки. Для `-t` и `CHECK_FOLDER_TIME` используется `sscanf()`;
код отвергает ноль, но не проверяет, что интервал положителен. Отрицательное
значение передаётся в `sleep()` после целочисленных преобразований и не
является поддерживаемым режимом. Для надёжного мониторинга используйте
положительный интервал и путь, помещающийся в буфер.

**Согласованность начального сканирования:** список сначала подсчитывается одним
обходом `readdir()`, затем выделяется массив и выполняется второй обход,
заполняющий его без отдельной проверки вместимости. Если каталог изменится
между проходами, добавление файла может привести к записи за границей массива.
На время запуска сохраняйте состав каталога неизменным; при рефакторинге
объедините оба прохода либо добавьте контроль ёмкости.

**Ошибки чтения:** `CRC32()` завершает цикл при `fread() == 0`, не проверяя
`ferror()`. Ошибка чтения может быть воспринята как конец файла и дать CRC32
неполного содержимого. Для использования в мониторинге целостности требуется
явная проверка ошибок ввода.

**Граница наблюдения:** набор файлов фиксируется при запуске, и для каждого
файла сохраняется открытый `FILE *`. Перед повторным расчётом CRC32 выполняется
`fseek()` на начало того же дескриптора. Изменение содержимого открытого файла
может быть обнаружено, но атомарная замена пути новым файлом через `rename()`
не приводит к переоткрытию файла и может остаться незамеченной. Новые файлы
в каталоге также не добавляются в наблюдаемый набор. Сканирование
использует `dirent.d_type == DT_REG`, поэтому символические ссылки и записи
с `DT_UNKNOWN` не попадут в список даже тогда, когда указывают на обычный
файл. Для иной семантики
необходимо отдельно менять сканирование каталога и жизненный цикл дескрипторов.
